# 开发路线图（2026-09-12）

> 本文回答三个问题：为什么是这个顺序、每一步做什么、什么情况下本文结论应该被推翻。
> 配套阅读：`2026-09-12-current-state.md`（现状证据）、`2026-09-12-reference-projects.md`（外部方案与 License 约束）。
> 读者是后续执行的任意模型/开发者：每一步都给出验收标准，不要只读"做什么"而跳过"不做什么"和"辩证"两节——那里写着我否决掉的方案，避免你重复提议已被否决的路线。

## 1. 治理约束（不可协商红线）

来自用户项目简报，效力高于本文任何建议：

1. **公共仓安全**：仓库 public。禁止提交 Cookie/Token/数据库/真实下载内容/本机绝对路径；每次提交前 `git status` + `git diff --cached` 人工检查；`git add .` 后无检查直接提交是违规行为。
2. **不重复造轮子**：新功能先查 core/ 是否已有实现、CLI/REST 是否已暴露、参考项目是否已有成熟方案（查 `2026-09-12-reference-projects.md` §1 速查表）。
3. **为需求重构，不为架构图重构**：只有当真实重复已出现、模块职责明显混乱、新功能受现有结构限制时才重构。
4. **禁止商业化**：不做邀请码/会员/内测资格/License 验证/在线账号强制登录/支付/SaaS。
5. **工程红线**：不引入 Redis/MQ/K8s/微服务等过度设计；这是个人/小规模工具，稳定 > 简单 > 好用 > 可维护 > 可扩展。
6. **Git 纪律**：不自动 push、不 force push、不删历史；提交原子化、`type: 中文描述` 格式。
7. **所有外部 API 调用必须有 RateLimiter**（现状已满足：API 层 2 req/s ± jitter）。
8. **上游同步线**（见 §3 辩证 E，这是战略资产）：不要做会切断与上游 jiji262 合并能力的大面积重写。

## 2. 北极星与总路线

```text
                CLI
Web ── REST API ── Core(Task Service)
Desktop ───────────┘
```

所有产品形态共享同一套核心。总顺序沿用简报的六阶段，并压缩为三个可执行视界：

```text
短期(1-2周)  卫生 + 核心体验        ← 对应简报阶段一
中期(1-2月)  结构收敛 + Task Service ← 对应阶段二+三
长期(3月+)   Web UI → DATA_ROOT → Docker → (可选)Desktop ← 对应阶段四五六
```

## 3. 路线辩证（重要：本文最该被传承的部分）

### 主线论证：依赖链决定顺序

```text
UI 的使用体验 ≤ REST API 的完整性 ≤ 任务模型/Task Service 的清晰度 ≤ 核心下载链路的稳定性
```

现状证据：核心链路稳定（593 测试、成熟的容错体系），但任务模型半完工（job 表未接线、状态机缺 CANCELLED）、API 是刻意裁剪的子集、编排逻辑三处手工同步。**在这条依赖链上，每一环的质量都是上一环的天花板**——先写 UI，就等于把"三处编排复制 + 内存任务"固化成第四个消费者。这就是顺序不可调换的原因。

### 被否决的备选方案

**A. "直接先做 Web UI，大不了先包现在的 4 个端点"**
否决理由：现有端点不能写历史、不能取消、不能看进度、任务重启即丢。UI 建在这种 API 上，要么做成残废，要么在 UI 层再糊一层绕过 API——制造第 4 份业务逻辑。
**何时翻案**：若用户出现一个"现在就必须在浏览器里粘贴链接下载"的真实场景，允许做一个纯调 `POST /api/v1/download` 的最薄页面，但必须书面承认这是债（在本文变更记录中登记），且不得为它新增任何 API 之外的逻辑。

**B. "一步到位大重构：先画好 core/parser|downloader|services|task 目录再逐步搬"**
否决理由：违反约束 3（为需求重构）；93 个文件级移动会让上游 merge 变成地狱（约束 8）；593 个测试的语义在搬移中易被破坏且无用户可见收益。
**何时翻案**：当 DownloadService 抽取（中期第 1 项）完成、且上游活跃度明显降低（以 3 个月无实质提交为准）时，目录级整理可作为独立任务重评。

**C. "先做 Docker / 部署产品化"**
否决理由：配置结构、API 形态、UI 形态都还在变；现在做 Docker 封装是给移动靶子焊外壳。约束见简报：Docker 是交付方式之一，不是开发前提。
**何时翻案**：收到"要在 NAS/服务器上常驻运行"的真实需求时，直接跳到长期第 3 项（Docker 正式化清单已备好），跳过 Web UI 也允许——Docker 与 UI 在路线上是并列项而非依赖项。

**D. "引入 F2 作为依赖，替代自维护签名与 token"**（真正的两难，值得保留辩论）
- 正方：F2 的 ABogus 满血版已开源且持续维护；token 族完整（ttwid/webid/verify_fp 我们没有）；Apache-2.0 可合法集成；签名失效时跟着 F2 升级即可。
- 反方：F2 是重型多平台库，其 ab 算法版本与抖音风控的耦合节奏未必匹配我们的调用模式；引入后配置体系、错误模型、代理链路都要适配；"升级跟随"前提是我们能跟上 F2 的 API 变迁（它自己也在 0.0.1.x 快速演进）。
- 当前裁决：**不引入**。我们的 X-Bogus/A-Bogus 静态复刻 + msToken 三级兜底当前可用（有测试覆盖）。
- **何时翻案**：当签名整体失效（现象：大面积 403/空 200 且换签名无效）且自研修复超过 2 天工作量时，优先评估"依赖 F2"与"Fork 其 abogus 单文件"两个选项，取侵入小者。

**E. "跟随上游 merge vs 自主分叉"**（隐含最重要的战略辩证）
- 上游 CLI 侧仍在活跃维护：msToken 兜底、门禁、增量窗口等修复持续免费产生。保持可 merge 性 = 免费获得红风控对抗成果。
- 代价：不能随意重排目录、重命名核心符号、换架构风格；中期所有重构必须是**增量式、局部式**的，让 merge 冲突可控。
- 推论：这不是"永远跟着上游走"——我们的分叉点是产品层（REST/Task Service/Web UI），上游恰好不做这些（它做闭源 Douzy），天然错位互补。

### 贯穿性判断

- **为什么中期第一件事是抽 DownloadService 而不是补 API 端点**：每加一个端点都是在三处重复的债务上加息。先还本金。
- **为什么 job 持久化放中期而不是立即**：内存队列对"本地单人 CLI"已够用；但接线成本低（表和方法都现成），且是 cancel/retry/历史/进度一切后续能力的前提，所以排中期第一梯队。
- **为什么不立项"拆 BaseDownloader"**：1643 行巨类属实，但在 593 测试保护下"触碰即抽取"（下次改画质逻辑时顺手游出画质模块）比独立重构更安全；独立立项会被约束 3 否决。
- **为什么 Python 版本要统一而不是维持三处口径**：AGENTS.md 的 3.8 兼容禁令直接决定语法可用集；口径不一导致"能用什么语法"靠考古。

## 8. 执行护栏（给下一个模型的开工前必读）

1. 动手前读 `2026-09-12-current-state.md` 对应章节 + 实际代码（行号可能已漂移，以代码为准）。
2. 先跑 `python -m pytest -q` 拿到动手前基线；交付时必须回到全绿。
3. 每个任务原子提交，`type: 中文描述`；提交前 `git status` + `git diff --cached` + 敏感文件复测。
4. 触碰共享目录（auth/cli/config/control/core/storage/tools/utils）的修复前，检查 D1 的最新裁决状态。
5. 遇到本文与代码现实冲突时，改文档不改事实：在下方变更记录追加一条说明再按新事实执行。
6. 不做本文与简报之外的功能（包括"顺手优化"）；发现无关坏味道只记录不修改。
7. **红线（用户两次重申）**：任何隐私/安全内容不得进 git。提交前逐条检查 `git diff --cached`；推送前对推送范围做敏感模式扫描；CI 的 Guard 步骤（`.github/workflows/ci.yml`）做机器兜底。`Downloaded/`、数据库、cookie 文件只读不动不提交。

## 9. 路线失效条件（何时推翻本文重推）

- 抖音风控重大升级使签名/token 链整体失效 → 短期插入"签名供给链修复"最高优任务并触发辩证 D 重评
- 上游停止维护（3 个月无实质提交）→ 约束 8 权重取消，中期重构可放宽尺度
- 用户明确产品方向变化（如"先 Docker 上 NAS"、"先做 UI"）→ 按辩证中各备选方案的翻案条件执行，并在变更记录登记
- 本 fork 开始产生自己的提交后，所有"91 提交均为上游作者"相关结论失效，git 卫生基线需重测
